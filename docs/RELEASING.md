# Подготовка релиза 1.x

## Ветки и версия документации

Эти документы описывают **1.x**. До переключения веток разработка находится в
`next`, а `main` содержит 0.6. После переключения:

| Ветка | Назначение |
| --- | --- |
| `main` | Основная разработка и документация 1.x |
| `legacy` | Сохранённая ветка 0.6; не источник установки 1.x |

Ветки ещё не переключены. Push изменений в `next` сам по себе не выполняет
перенос и не публикует 1.0. Тег
[`v0.6.2`](https://github.com/amirotin/telemt_panel/tree/v0.6.2)
остаётся неизменным источником кода и документации старого релиза.

Порядок переключения после отдельного подтверждения:

1. Проверить актуальные вершины удалённых веток и сохранить текущую `main`
   в `legacy`, включая исправления после 0.6.2. Не перезаписывать существующую
   `legacy`, если её история отличается.
2. Сделать проверенную ветку 1.x новой `main`. Истории поколений независимы:
   это не обычное слияние. Согласовать защиту веток, ветку по умолчанию и
   цели открытых PR; не терять указатель на старую историю.
3. В CI переключить push/pull_request с `next` на `main`. Обновить вводный
   блок README и удалить временную команду установки из `next`. Проверить
   ссылки на ветки во всех Markdown-файлах и workflows. Ссылки установки
   на опубликованные теги не требуют замены.
4. Сохранить старую документацию в `legacy`; указать там, что актуальная
   панель находится в `main`. Не заменять старые примеры конфигурации на 1.x.
5. Проверить CI на новой основной ветке. Создание тега и публикацию релиза
   выполнить отдельно по процедуре ниже; переименование ветки не означает,
   что `v1.0.0` уже опубликован.

## Локальная сборка без публикации

Используйте Go из `go.mod` и Node.js 22. Для локальной разработки запускайте
сборку в отдельной копии исходников: `make release` создаёт `release/` и frontend
артефакты. Они не должны попадать в Git.

```sh
make release VERSION=1.0.0-rc.1
RELEASE_DIR="$PWD/release" RELEASE_VERSION=1.0.0-rc.1 \
  go test -count=1 -run '^TestReleaseContract$' ./internal/update/
```

Команды не создают тег и не публикуют релиз. Старые результаты из другого
запуска лучше предварительно перенести в отдельный каталог: контракт отвергает
лишние файлы и каталоги в `release/`.

## Переходная матрица 0.6.2 → 1.0

| Профиль | Архитектуры | Драйверы истории | Лимит бинарника |
| --- | --- | --- | --- |
| full | x86_64, aarch64 | memory, sqlite | 32 МиБ |
| lite | x86_64, aarch64 | memory | 16 МиБ |

Архитектуры соответствуют официальным сборкам Telemt: x86_64 и aarch64.
ARMv7, MIPS и другие 32-битные цели не выпускаются. Вариант Telemt x86_64-v3 —
CPU-оптимизация, не отдельная архитектура панели: наша сборка x86_64 использует
`GOAMD64=v1` и работает также на v3-совместимых процессорах.

Все бинарники статические, `CGO_ENABLED=0`, с `-trimpath`.
Для переходного релиза сохраняются имена с `linux-gnu` и
`linux-musl`: это одинаковые бинарники под совместимыми именами, а не разные libc.

- Full: `telemt-panel-<arch>-linux-<gnu|musl>.tar.gz`.
- Lite: `telemt-panel-lite-<arch>-linux-<gnu|musl>.tar.gz`.

Итого 4 уникальных бинарника, 8 архивов и 8 файлов `<archive>.sha256`.
В каждом архиве — только
`telemt-panel`, обычный файл с mode 0755 и UID/GID 0. Старый updater 0.6.2
поддерживает x86_64/aarch64 и выбирает full; нужные ему имена сохранены.

Контракт проверяет весь набор, суммы, архивы/CRC, ELF-архитектуру и endian,
статическую сборку, профили, лимиты и идентичность aliases. Он использует настоящий
extractor updater. Для native-архитектуры выполняет `version`; для остальных
проверяет ELF/build metadata и наличие строки версии, не эмулирует запуск.
В build metadata с `-trimpath` нет `-ldflags`, поэтому версия не читается из них.

## Публикация

Workflow `release.yml` запускается при push тега `v1.*`. Он проверяет формат тега,
собирает архивы и запускает контракт **до** `gh release create`. Релиз сначала
создаётся как draft; публикация выполняется только после успешной загрузки всех
assets. Ошибка загрузки оставляет draft для ручной проверки, а не публичный
неполный релиз. Тег с prerelease
частью (например `v1.0.0-rc.1`) создаёт prerelease. Дефис только в build metadata
не меняет статус стабильного релиза.

Создание/push тега — отдельное осознанное действие после проверок перехода и
восстановления. Локальные тесты и actionlint не подтверждают разрешения токена,
доступность GitHub или успешную загрузку assets: это проверяется настоящим
публикационным прогоном отдельно. Лимиты full/lite не повышайте молча при ошибке
сборки; сначала выясните причину изменения размера.
