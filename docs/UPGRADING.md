# Обновление существующей установки

Обновления из панели не требуют checksum assets и не проверяют хэш архива.
Начальные проверки скачиваемого релиза остаются в `install.sh`.

Повторный запуск `install.sh` с существующим конфигом обновляет бинарник и при
необходимости выполняет описанную ниже миграцию пути Telemt и прав обновления.
Сервисный пользователь, настройки службы и правила firewall сохраняются.
Для нового протокола обновления установщик добавляет отдельную службу и короткий
скрипт запуска, а в основной службе меняет команду запуска на этот скрипт.
Переменные первичной установки не переопределяют работающий сервис при обновлении.

## Обновление из панели

Новая управляемая установка запускает `update-worker` из того же бинарника в
отдельной службе. Worker сохраняет предыдущий бинарник, останавливает панель,
делает согласованный снимок её конфига, состояния и SQLite, заменяет бинарник и
запускает службу. Успех подтверждается двумя последовательными ответами готовой
панели с ожидаемой версией. Ошибка запуска или проверки вызывает откат бинарника
и снимка данных с проверкой прежней версии. При обновлении Telemt панель продолжает
работать; отдельный worker проверяет готовность и версию Telemt.

Журнал и блокировка находятся в `updates.worker_state_dir`, по умолчанию
`data_dir/updater`. На OpenWrt установщик выбирает постоянный каталог рядом с
конфигом, поскольку стандартный `data_dir` размещён в RAM. Если процесс обновления
прерван, скрипт запуска выполняет восстановление
до старта панели; при повреждённом основном бинарнике используется `.bak`.
После подтверждённого результата временные архивы, снимок и `.bak` удаляются.
Незавершённый откат сохраняет резервные файлы для следующей попытки.

Постоянной копии helper нет. Root-установки выполняют команды напрямую,
непривилегированные используют точные команды sudoers. Старый helper удаляется
обычным установщиком после успешного перехода. Обновление только бинарника
сохраняет прежний совместимый способ работы до запуска установщика; существующие
права sudo не позволяют самой панели создавать новые системные службы.

Исторические бинарники без `update-worker --protocol` не подходят для этой схемы.
Попытка установить такую версию отклоняется до остановки и замены панели.
Переход обратно на старую схему установщиком также не выполняется автоматически.

## Порядок

1. Скрипт читает защищённую копию конфига, получает новый бинарник и проверяет
   checksum и структуру архива. Явный `--binary` означает доверенный локальный файл.
2. Новый бинарник разбирает TOML. Проверяются пути, имя сервиса, профиль full/lite;
   версия скачанного бинарника должна соответствовать тегу релиза.
3. После подтверждения скрипт проверяет текущий HTTP/HTTPS-ответ и сохраняет
   резервный бинарник в закрытом каталоге рядом с установленным:
   `.telemt-panel-backup.XXXXXX/binary`.
4. Если кандидат поддерживает worker, установщик подготавливает отдельную службу,
   скрипт восстановления и точные sudoers без копии helper. Для исторического
   кандидата сохраняется прежняя схема: непривилегированная управляемая
   systemd-служба получает stable helper, root policy v2 и sudoers. Фактический
   пользователь берётся из systemd; числовой UID разрешается в имя. Root-служба
   с `auto`/`direct` обновляется без создания helper и policy; явно выбранный
   `sudo` сохраняет защищённый механизм. При миграции прав стандартный `/bin/telemt` при `/bin → /usr/bin`
   меняется на `/usr/bin/telemt`; старый и новый пути показаны до подтверждения.
   Сервис останавливается, новый файл устанавливается атомарным переименованием,
   сервис перезапускается. Проверяется health с **точной версией**, включая TLS/SNI;
   один HTTP 200 не считается подтверждением запуска новой панели.
5. Если замена, публикация прав, restart или проверка не удались, исходные
   конфиг, unit/init-скрипты, wrapper, регистрация worker, helper, policy и sudoers
   возвращаются **до** запуска прежней панели.
   Восстанавливается резервный
   бинарник и проверяется прежний ответ панели. Для systemd сбрасывается failed-
   состояние только этого сервиса, чтобы StartLimit не блокировал восстановление.

Backup остаётся после успеха и после отказа. Его путь указан в выводе. При
неуспешном автоматическом восстановлении скрипт завершится с ошибкой и попросит
восстановить этот файл и перезапустить сервис вручную. Даже успешный откат не
превращает неудачное обновление в успешный exit 0.

Сохраняются владелец, группа и режим резервного файла. GNU cp также сохраняет
расширенные атрибуты/ACL; возможности BusyBox ограничены его реализацией cp.
Это восстановление бинарника, а не резервная копия БД, state или всей системы.
Произвольная несовместимость форматов данных между версиями этим не исправляется.

## Особенности

- Если задан `base_path`, reverse proxy должен сохранять этот префикс.
  Запросы без него теперь возвращают 404. Перед обновлением замените Caddy
  `handle_path` на `handle` или уберите завершающий `/` из nginx `proxy_pass`.
  Примеры — в [CONFIG.md](CONFIG.md#за-nginx-или-caddy).

- `--dry-run` выполняет загрузку/проверку во временном каталоге, но не заменяет
  бинарник и не перезапускает сервис. Содержимое записываемых файлов не печатается.
- `--no-start` оставляет backup и новый бинарник без проверки запуска. При
  миграции systemd-прав панель остаётся остановленной; при обновлении только
  бинарника старый процесс продолжает использовать прежний образ до restart.
- Для проверки нужны `timeout`, `sha256sum`, `readlink` и исполняемый временный
  каталог. При `noexec` на `/tmp` выберите его явно, например
  `TMPDIR=/var/tmp sh install.sh`. Скрипт не меняет mount-политику системы.
- `--variant` задаёт профиль явно. Для локального `--binary` без `--variant`
  профиль берётся из проверяемого бинарника; lite с SQLite-конфигом отклоняется.
- Конфиг 0.6 читается тем же Go-декодером, что при запуске, и остаётся побайтно
  прежним. Одноразовый перенос состояния выполняется при старте: check/off,
  интервал 6 часов, без автоустановки. JWT требует нового входа.
- Установщик должен запускаться при отсутствии другой операции обновления.
  Механизм не обещает восстановление при аварии питания или принудительном SIGKILL.

Самообновление из веб-интерфейса 0.6.2 — другой путь: старый процесс может быть
остановлен systemd раньше проверки результата, поэтому при падении нового
бинарника **автоматического отката 0.6.2 нет**. Сохранённый им `done` не доказывает
успех. Для контролируемого перехода используйте актуальный установщик.

## Восстановление прав в прежних установках без worker

Этот раздел относится к старому протоколу. Установку с worker восстанавливают
обычным запуском установщика; `repair-privileges` для неё не применяется.

Автоматическая миграция принимает стандартные старые правила `root/NOPASSWD`.
Политики с паролем, дополнительными ограничениями или непонятным форматом
требуют явного `repair-privileges`, чтобы обычное обновление не расширяло права.

Самообновление из веб-интерфейса не меняет старые sudoers. Пока root-оператор не
установит отдельный stable helper, protected policy v2 и точные helper-команды, 1.x показывает ручной
режим обновления. Автоматического перехода на legacy `cp/chmod/mv` нет.

Обычное обновление актуальным installer от root автоматически переносит права
управляемой systemd-службы с текущим TOML. Второй запуск repair не нужен.
Для nonroot-службы старые точные sudo grants должны уже разрешать указанные
бинарники, staging и сервисные команды: установщик проверяет их read-only через
sudo до остановки службы. Изменение runtime-конфига не создаёт новых root-прав;
если старые разрешения не совпадают, требуется явная repair-команда после
проверки путей и учётной записи. Все предки helper, policy и sudoers проверяются
на root-владение и отсутствие групповой/общей записи; root sticky ancestors
вроде `/tmp` допускаются, непосредственные защищённые каталоги остаются строгими.
Явные `privileges.mode = "manual"` и `"direct"` сохраняются без sudo grants;
уже согласованная policy v2 и helper сохраняются. Если существующие root-файлы
принадлежат другой установке или их привязку нельзя проверить, обновление
отклоняется до остановки; требуется отдельная проверка и явная repair-команда.
Для отдельного восстановления уже установленной 1.x выполните:

```sh
sh install.sh repair-privileges --user telemt-panel
```

Вместо `telemt-panel` укажите фактическую учётную запись службы. Команда
показывает policy path, бинарники, staging и выбранную учётную запись;
останавливает панель, публикует root-owned stable helper `0755`, создаёт
root-owned policy v2 `0600` в отдельном каталоге `0700`, проверяет её через
stable helper `privileged --policy … inspect`, проверяет sudoers
через visudo при его наличии и заменяет файлы атомарно. Бинарники и
unit/init-скрипт сохраняются. При стандартном merged-/usr меняется только
`updates.telemt_binary_path`; остальные значения, секреты и комментарии сохраняются.
Конфиг проверяется опубликованной CLI RC3, backup рядом с конфигом сохраняет
владельца, группу и режим (GNU cp также ACL/xattrs). При отказе возвращаются исходный
конфиг и предыдущие helper, policy и
sudoers; при неудачном restart выполняется такой же откат. `--no-start` оставляет
панель остановленной после успешной миграции.

Native policy по умолчанию: `/etc/telemt-panel-privileged/policy.json`;
Entware: `/opt/etc/telemt-panel-privileged/policy.json`. Поле
`privileges.policy_path` может выбрать другой root-owned путь, но sudoers
разрешает только этот точный путь. Каталог runtime-конфига принадлежит
пользователю панели и не подходит для хранения root-authority policy.

Native stable helper: `/usr/local/libexec/telemt-panel-privileged`; Entware:
`/opt/libexec/telemt-panel-privileged`. `privileges.helper_path` задаёт тот же
защищённый путь в runtime-конфиге. Это отдельная копия проверенного panel binary;
web self-update сохраняет её. В policy v2 helper
не пересекается с replaceable binaries, backup и locks ни путём, ни inode.
При старой policy v1 нужен explicit repair. Если main binary уже повреждён или
не поддерживает новую CLI, передайте проверенный текущий binary через
`--binary /path/to/telemt-panel` для root-operator repair. Release archive остаётся
с одним бинарником; установленная копия helper требует дополнительного места
только там, где он установлен для sudo/repair. Новая установка с запуском панели от root
(в том числе OpenWrt и Entware) использует `direct` без создания helper/policy.

Все пути должны быть абсолютными и каноническими. Repair и обычное обновление
systemd автоматически исправляют parent aliases `/bin → /usr/bin` и
`/sbin → /usr/sbin`, включая отсутствующий ключ стандартного пути.
Другие aliases, symlink самого бинарника, неканонический `data_dir`, DynamicUser
и непонятные формы TOML отклоняются с объяснением до публикации. Для автоматической
правки TOML нужны обычные таблицы, bare keys и строки на одной строке;
многострочные массивы допускаются, многострочные строки требуют явной правки.
Конфиг 0.6 и другие init systems пока сохраняют прежний путь обновления только
бинарника; права восстанавливаются отдельной repair-командой.
Для произвольного custom service без
управляемого stop/restart-скрипта остановите его и подготовьте policy/sudoers
вручную. Не запускайте runtime во время изменения policy paths.

Root-owned policy не ограничивает полномочия скомпрометированной учётной
записи, которой разрешено устанавливать бинарник root-сервиса. Helper защищает
файловую операцию и фиксирует пути; это не изоляция такой учётной записи.

## Что переносится из 0.6.2

Первый запуск 1.x со старым TOML сохраняет адрес, HTTPS/ACME, пути, логин и пароль.
Старый эффективный срок сессии по умолчанию остаётся 24 часа, не заменяется
на 720 часов. JWT-сессии 0.6 не переносятся — потребуется новый вход.
Если старый файл содержал открытый пароль, стабильный bcrypt-хеш сохраняется
в защищённом state-файле. Повторный запуск не генерирует новую идентичность.

Состояние инициализируется один раз: включённые проверки версий → `check`,
выключенные → `off`, интервал 6 часов, без автоматической установки. Последующие
изменения настроек 1.x не перезаписываются значениями старого TOML.
Старые defaults формы пользователей и лимиты списка релизов остаются только
в архиве с предупреждением. Аккаунты, квоты и конфигурация Telemt не меняются.

Локальные GeoIP-файлы проверяются и копируются в управляемый каталог без скачивания.
При ошибке вход остаётся доступным, в журнале появляется
`legacy_geoip_activation_failed`; уже настроенный GeoIP 1.x не сбрасывается.
Ключ подписок создаётся один раз, но сами страницы подписок автоматически не включаются.

Для отдельной офлайн-подготовки доступна команда:

```sh
telemt-panel config import-state --config /etc/telemt-panel/config.toml
```

Она отдельно инициализирует `data_dir/panel-state.json`; при обычном обновлении
это делает первый запуск 1.x. Выполняйте её при остановленной панели, от пользователя службы: назначение должно
быть пустым либо уже иметь отметку этого переноса. Команда не запускает сервисы,
не открывает историю и не меняет исходник. `already_imported` не меняет состояние;
`imported_*` описывают исходный перенос, а не текущие настройки администратора.

Все offline imports, включая `config import-state`, требуют свободного
`data_dir/.panel.lock`. Выполняйте import при остановленной панели; если runtime
держит директорию, команда сразу возвращает `data_dir_in_use` без изменения
state/history. После graceful exit или crash lock освобождается ОС. Не удаляйте
lock-файл: постоянный inode нужен для исключения одновременных владельцев.

`store export` разрешён при работающей панели: он читает existing state и
committed SQLite history через read-only WAL snapshot, не открывает второй
writable runtime и не создаёт отсутствующую БД. Для включения ожидающих SQLite
samples и session touches остановите панель, дождитесь Close/flush и выполните
CLI export. В режиме memory CLI сохраняет
только persistent state; история RAM принадлежит текущему процессу.
`pending` и `not_applied` перечисляют оставшуюся обработку и архивные группы.

В режиме старого TOML веб-изменение HTTPS и команды `store export/import`, которым
нужна текущая схема, недоступны. Для них используйте явный экспорт ниже.

## Экспорт конфига в текущую схему

После успешного запуска 1.x со старым конфигом можно создать TOML текущей схемы.
Это необязательный отдельный шаг: обновление бинарника само исходный TOML не меняет.
Команда требует уже инициализированный `data_dir/panel-state.json`; одного
`config import-state` недостаточно. Сначала запустите 1.x в режиме совместимости
и убедитесь, что вход работает.

1. Остановите панель и сохраните резервную копию конфига и `panel-state.json`.
2. От пользователя службы, из того же рабочего каталога, выполните:

   ```sh
   telemt-panel config export --config /etc/telemt-panel/config.toml --out /etc/telemt-panel/config.1x.toml
   telemt-panel config check --format current --config /etc/telemt-panel/config.1x.toml
   ```

3. Проверьте отчёт `pending` и новый файл. Он содержит секреты, создаётся с правами
   `0600` и должен принадлежать пользователю службы. Каталог должен существовать;
   существующий файл или символьную ссылку команда не перезапишет.
4. Для установки через `install.sh` сохраните стандартный путь
   `/etc/telemt-panel/config.toml`: отложите старый файл в защищённую резервную
   копию и явно замените его проверенным экспортом, сохранив владельца службы.
   Сам экспорт этого не делает. Для самостоятельно настроенного запуска можно
   вместо замены явно поменять `--config` службы, сохранив пользователя и рабочий
   каталог (для systemd после правки unit нужен `systemctl daemon-reload`).
   Запустите панель и проверьте вход, адрес и транспорт. При проблеме остановите её
   и верните прежний файл или путь. Резервную копию старого TOML не удаляйте.

Экспорт работает без сети, БД истории, открытия сертификатов и запуска служб.
Он не изменяет исходник или состояние: сохраняет адрес, base_path, доверенные
прокси, пути, срок сессии, действующий bcrypt-хеш и ключ подписок. Пароль открытым
текстом и старый JWT-ключ в новый файл не попадают. Настройки автообновления,
GeoIP, passkeys и прочие данные 1.x остаются в том же `panel-state.json`, а не
дублируются в TOML. Нельзя менять `data_dir` одновременно с переключением формата.
Относительные пути по-прежнему отсчитываются от рабочего каталога процесса,
не от расположения нового TOML.

`pending` содержит только названия ещё не применённых старых групп:

- `geoip_activation`: локальные базы ранее не удалось подключить; после перехода
  на текущий TOML автоматических повторов legacy-импорта нет. Подключите базы
  в настройках GeoIP. Уже работающая конфигурация GeoIP не сбрасывается.
- `unused_telemt_config_path`, `inactive_acme_cache`: сохранённые неиспользуемые
  пути; Telemt редактируется через API, файлы по этим путям не удаляются.

В `not_applied` отдельно перечислены архивные `user_defaults` и `release_limits`.
В 1.x остаются текущие пресеты создания пользователей и список до 10 новых / 3
старых версий. Старые значения не применяются ни при запуске, ни при создании
пользователя и не ожидают будущего импорта. Это не меняет существующие аккаунты
Telemt, их квоты или резервные копии обновлений.

Если пароль в старом TOML изменён после последнего запуска, сначала запустите 1.x
с этим файлом: экспорт не генерирует новую идентичность вместо уже используемой.
После переключения доступны команды, требующие текущую схему, и веб-настройка HTTPS.
